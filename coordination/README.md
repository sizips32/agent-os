# Coordination source contract

This additive adapter and its synthetic tests can be registered as a separate version beside the existing operating helper. Registration grants no task execution, publication authority or per-request owner approval. The original `ohha-control` helper and skill remain intact.

The adapter's default live approval provider denies dispatch. `registered_cli.py` also denies before discovery or ledger writes when a per-request approval is missing. Its owner-operated terminal review shows the exact target, prompt hash, budgets and expiry, and requires the full proposal hash to be entered. No affirmative flag or environment bypass is provided. Existing-session identity, reservations, native result hashes and late collection remain enforced. Timeout and uncertain reservations never authorize another send. The legacy CLI in this source package still denies send/publication commands.

`npm run test:coordination` uses temporary profile DBs, fake processes and synthetic source captures. It checks the specialist → worker → source/claim review → task projection contract, duplicate refusal, approval mismatch, target replacement, native final identity and late collection, as well as separate registration, default denial and owner-binding substitution. Synthetic completion remains unverified. The application bundles the task reader only; it does not automatically install this transport package. The owner explicitly omitted the real collaboration test, so actual collaboration remains unverified.

No profile databases, actual sessions, operator approval files, transcripts, notes, credentials or owner project configuration are included.

`operator_approval.py` freezes an exact proposal, requires the reviewed proposal hash, caps lifetime/turn/time budgets and writes one owner-private receipt without overwriting earlier receipts. The registered entry connects this port to a foreground owner terminal; an agent must not drive the approval prompt. This is a local consent workflow, not OS isolation against other code running as the same user. It adds no API key, OS permission, daemon or login item.

`install.py --approved-roots FILE --seat-inventory FILE` verifies that the locally approved roots match the existing controller inventory, creates a content-addressed release under `~/.hermes/ohha-coordination/releases`, and registers only a separate `ohha-coordination` skill for Giselle. It does not call the helper or migrate the central ledger. Actual roots are stored in a private local file, never copied into this repository. Fixture project paths are never used by the registered live entry. Worker discovery/control still requires a genuine foreground empty Herdr-managed shell; no context spoofing or focus fallback is allowed. Specialist requests use only the unique existing canonical session and refuse active-session conflicts.

Rollback removes only the newly added skill symlink, or repoints the new helper's `current` to its recorded previous release. Preserve releases, approval records and any uncertain task reservations for inspection; do not remove the existing `ohha-control` skill, helper, task data or collaboration modules. Installation and file checks do not prove that a running agent has refreshed its skill catalogue. Live publication review remains blocked.
